# SaaS Churn Intelligence

End-to-end subscription analytics platform: predicting customer churn, decomposing monthly recurring revenue, quantifying business impact through customer lifetime value, monitoring for data drift, and testing retention interventions with proper experiment design — built on a persistent, incrementally-ingested data pipeline rather than a static one-off CSV read.

---

## What this project covers

| Area | Techniques |
|---|---|
| Exploratory Analysis | Churn rate segmentation, distribution analysis, correlation heatmap |
| Cohort Analysis | Retention matrix, cohort heatmaps, decay curves |
| Revenue Analysis | MRR trend, MRR decomposition (new vs. churned revenue), ARPU |
| Churn Prediction | Logistic Regression vs. XGBoost, ROC/AUC, precision-recall |
| Model Explainability | SHAP values, force plots, business translation of model drivers |
| Unit Economics | Kaplan-Meier survival-based CLV, LTV:CAC ratio, payback period, scenario modeling |
| Survival Analysis | Cox Proportional Hazards — independent, quantified hazard ratios per churn driver |
| Live Data Pipeline | Persistent DuckDB store, upsert-safe customer records, incremental monthly ingestion, full audit trail |
| Revenue Retention | Net Revenue Retention (NRR) from a simulated monthly revenue panel — expansion/contraction/churn decomposition |
| Model Monitoring | Population Stability Index (PSI) feature-drift detection, performance-drift detection, auditable retraining pipeline |
| Experimentation | A/B test framework for retention interventions — proper sample-size calculation, two-proportion z-test, confidence intervals |
| SQL Analytics | DuckDB queries for all business metrics |
| Dashboard | Interactive Streamlit app |

## Setup

```bash
# 1. Clone the repo and create a virtual environment
git clone https://github.com/tanekcodes/saas-churn-intelligence.git
cd saas-churn-intelligence
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Generate the datasets
python data/generate_data.py
python data/generate_monthly_panel.py

# 4. Run the notebooks in order (01 → 11)
jupyter notebook

# 5. Launch the dashboard
streamlit run dashboard/app.py
```

> **Note:** Run notebook `04_churn_prediction.ipynb` before the dashboard or notebooks 05/06/10/11 — it trains and saves the XGBoost model. Run `08_live_data_pipeline.ipynb` before `10_drift_detection_retraining.ipynb` if you want the persistent DB populated first (notebook 10 also works standalone — it trains its own baseline/comparison models directly).

**Option A — inside a notebook:**

```python
conn = duckdb.connect("data/vertex_churn.db")
result = conn.execute("SELECT * FROM customers LIMIT 10").df()
```

**Option B — DuckDB CLI:**
```bash
duckdb data/vertex_churn.db < sql/02_churn_metrics.sql
```

## Key findings

**Churn & prediction**
- **Month-to-month customers churn at roughly 4.9x the rate** of two-year contract customers (68.3% vs. 14.0% cumulative churn incidence) — contract conversion is the highest-leverage retention lever, confirmed independently by four separate methods below.
- **The XGBoost model achieves ~0.80–0.87 ROC AUC** depending on the data slice (5-fold CV mean 0.784 on the full dataset), with contract type, tenure, and monthly charges as the top predictive features (confirmed by SHAP).

**Customer lifetime value**
- **CLV is estimated via Kaplan-Meier survival analysis**, not by inverting the churn model's predicted probability — see Methodology Notes for why the naive approach silently understates real lifetimes.
- **Expected customer lifetime by contract:** month-to-month ~22.3 months, one-year ~52.6 months, two-year ~65.7 months. **LTV:CAC by segment:** 4.5x / 10.4x / 13.1x — portfolio-weighted average ~7.8x, above the 3x SaaS health benchmark.
- **A 5-point reduction in month-to-month churn** would unlock approximately **$793K in incremental portfolio CLV**.

**Independent confirmation via Cox Proportional Hazards** *(notebook 07)*
- Controlling for internet service, senior-citizen status, and monthly charges simultaneously, **contract length remains the single strongest independent churn driver** — one-year contracts show roughly a 90% lower churn hazard than month-to-month, two-year contracts roughly 97–98% lower, both overwhelmingly statistically significant. Fiber-optic internet customers show meaningfully higher hazard even after controlling for contract type — a real, independent risk factor worth its own retention attention.

**Net Revenue Retention** *(notebook 09, built on a simulated monthly revenue panel)*
- Trailing-12-month NRR runs **~81%** and is broadly consistent across contract segments (80.8%–82.3%) — meaning the revenue erosion is a **churn** problem, not an expansion/contraction problem; upsell/downgrade dollar volume is small relative to churned-customer revenue loss. This distinction matters because it points toward retention investment over upsell-motion investment as the higher-leverage fix.

**Model monitoring** *(notebook 10)*
- A simulated 25% price shift on newly-arrived customers was correctly flagged by Population Stability Index monitoring (MonthlyCharges PSI far above the 0.25 alert threshold), and the shift caused a **real, measured AUC drop from 0.874 to 0.773** on the shifted population — confirming the model would have silently degraded without monitoring. Retraining on the combined dataset recovered performance to **0.867 AUC** (+0.094 improvement), with the retrain decision and its reasoning fully logged.

**Retention experimentation** *(notebook 11)*
- A properly-sized, simulated retention-intervention experiment correctly recovered a known ground-truth effect (true effect 8.0 points, recovered 10.6 points, 95% CI [7.0%, 14.2%] — correctly containing the true value). A deliberately underpowered version of the *same* experiment (n=30/arm instead of the required ~542/arm) returned a **non-significant, wrong-direction result despite the same true effect being present in the data** — a concrete demonstration of why sample-size calculation has to happen before an experiment runs, not after.

## Methodology notes / known limitations

- Both datasets are **synthetic**. The cross-sectional customer table (`data/generate_data.py`) mirrors the structure and statistical properties of the public IBM Telco Customer Churn dataset. The monthly revenue panel (`data/generate_monthly_panel.py`) is a simulated month-by-month billing trajectory built on top of it, specifically to make Net Revenue Retention computable — the underlying cross-sectional data has no native longitudinal revenue history, so this was a deliberate addition rather than something extracted from the base dataset.
- CAC ($250) and gross margin (75%) are illustrative assumptions, not fitted from data — see constants at the top of `src/clv.py`.
- The Kaplan-Meier fit for month-to-month customers is restricted to their observed tenure range (the synthetic generator caps month-to-month tenure at 35 months); RMST beyond that is a flat extrapolation of the last estimated survival probability.
- **CLV methodology, in detail:** the churn classifier predicts a cross-sectional "will this customer ever churn" label, not a monthly hazard rate. Using `1 / churn_probability` as an expected-lifetime proxy conflates these two different kinds of probability and silently understates real customer lifetimes by roughly an order of magnitude. `src/clv.py` instead estimates expected lifetime as the restricted mean survival time (RMST) from a Kaplan-Meier curve fit on each segment's actual observed `tenure` and `Churn` outcomes.
- **Drift and A/B test findings are demonstrated against deliberately-introduced synthetic shifts/effects**, not naturally-occurring ones — this is intentional: it's the only way to validate that the detection and analysis code actually works correctly (i.e., that PSI really does flag a shift that's known to exist, and that the z-test really does recover an effect that's known to be present), the same logic used to validate the drift module's own unit tests.
- The NRR calculation's "month" is customer-relative (month 1 = each customer's own first billed month), not a shared calendar month — this keeps it consistent with the cohort-analysis convention used elsewhere in the project, but means NRR trends reflect "months since signup" cohort aging rather than calendar-time company performance.
